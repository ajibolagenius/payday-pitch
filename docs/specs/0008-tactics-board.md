# 8. Tactics board: edit a formation, save it as your own tactic, play it

**Date**: 2026-10-25
**Status**: Accepted

## Summary

A user takes any built in formation, changes each position's share on the pitch, and saves that as their own tactic with a name. The board shows real naira amounts while they drag the numbers around, so the choice feels like money, not percentages. Saving never breaks anything they already played: every save is a new pinned version, and past matches keep pointing at the version they used. The app also recommends a shape based on the user's own income, costs, and savings, and warns when the shape gets risky, but it never blocks a save and it never changes anything on its own.

## Context

The first match loop (spec 0007) ships six built in formations. A person picks one and plays it. That is enough for a demo and not enough for a tool someone returns to monthly: real lives do not match a stock shape. Fixed costs are higher than 40 percent, an emergency fund is already full so the goalkeeper spot is wasted money, a debt needs more room in midfield. The product promise in the scope is that the user can "switch tactics as life changes", which requires them to own the shape, not only borrow one.

Spec 0004 already built the tables for this, but no code reads or writes them. `user_tactic` and `user_tactic_version` exist with row level security, grants, triggers, and a JSONB split column summing to 10000 basis points. The `match` table is already designed for tactic sourced matches: it carries `source_kind`, `tactic_id`, `tactic_version_id`, and a copied `shape_name`. So the data decision was taken eleven slices ago; this feature is the first real use of it.

Three forces shape the design. The money rules are binding and already decided (spec 0001, spec 0004): integer minor units, no floats, the two step split where the defense zone always equals the real fixed cost total, largest remainder allocation. A match and its lines are all or nothing, which is why spec 0007 put the write inside one `security definer` Postgres function rather than a chain of action calls. The app plans and tracks only, it never touches a bank, so its voice is coaching, never gatekeeping.

Two gaps are load bearing and are decided here. `play_match` accepts only a library `p_shape_id` and hardcodes a twelve spot check, so a tactic sourced match cannot be played today. Nothing in the database or the domain computes emergency fund progress, which the 3 to 6 month nudge needs. The consequence of not deciding: `/develop` invents both, and the second one gets invented twice when Season view needs the same number.

> ⚠️ Premise note: editing a defender's share is not what it appears. Under spec 0004's split rule the DEF zone total is fixed at the user's real cost total, so a DEF stepper only changes which defender receives more of the same pool, never how much of income goes to defense. Two consequences follow, and the build must meet them rather than hope users guess them. First, the "costs over half of income" warning is a fact about the user's life that no share change can fix: the copy has to point at a base formation with a bigger defense share, or at the costs and income themselves. Second, a user who expects to lower their defense share will find the control inert and will conclude the board is broken. The mitigation chosen here is labelling: the zone reads as covering their costs, the pool shows as a locked figure, and the clamp message names the reason. If that reads as too subtle for the first release, the alternative is locking DEF spots to equal shares and editing only GK, MID, FWD, BENCH, which contradicts the scope's "each position's percentage" and is not recommended.

## Requirements

**User stories**:

- As a salary earner whose real costs do not fit a stock shape, I want to adjust each position's share and save it under my own name, so that my plan matches my life.
- As a user editing shares, I want to see the naira amount at every position change as I edit, so that I am choosing money, not numbers.
- As a user clearing a debt or filling an emergency fund, I want the app to suggest a shape that fits my current numbers and tell me why, so that I know which way to tune.
- As a user tempted to zero out my emergency fund, I want a warning, not a locked button, so that the plan stays mine.

**Acceptance criteria**:

- **AC-1**: From any library formation the user changes each position's share with plus and minus steppers in 50 basis point steps, or types an exact share, and the planned amount at every spot updates on the pitch before any save.
- **AC-2**: The user saves the edited shape as a named tactic. The name is 1 to 30 characters, unique per user, and a duplicate is refused with a clear message. A user may hold at most 5 saved tactics; at the limit the save action refuses with a message naming the cap and telling them to delete one.
- **AC-3**: Every save inserts a new `user_tactic_version` row and moves `is_current` to it. A match already played keeps its own pinned `tactic_version_id`, and its displayed planned amounts are unchanged by any later edit.
- **AC-4**: The total reaches 10000 basis points before a save, with no arithmetic step for the user. Raising a non DEF spot takes from BENCH, then from the largest other non DEF spot when BENCH is exhausted. Lowering a non DEF spot gives back to BENCH. Editing BENCH itself pulls from or gives to the largest non DEF spot. DEF spots are exempt: their shares only redistribute the fixed cost pool, so the zone total never moves.
- **AC-5**: A warning shows when the user's real fixed cost total exceeds 50 percent of income, and separately when the goalkeeper share is 0. Both appear inline on the board as the user edits, and again on the review step before playing. Neither blocks a save.
- **AC-6**: Once the goalkeeper savings reach 3 months of defense costs, using spec 0004's definition (the sum of `actual_minor` on GK lines across active matches, over the last active match's frozen DEF planned total), the board shows a nudge to consider moving that share forward, with one tap that loads the `4-3-3` shape into the board. It is a shortcut, never an automatic change. When no GK payment has been logged the nudge stays hidden, and when a debt is outstanding the one card carries the debt rule instead.
- **AC-7**: The tactics page shows one suggestion card naming a library formation and giving the reason, chosen by the first rule that fires, in this order: an outstanding debt gives `5-4-1`, a fund at 3 months or more gives `4-3-3`, fixed costs above half of income gives `5-3-2`. When no rule fires there is no card. Every name is a live, non deprecated row in the formation library, and the reason matches that shape's own `when_to_play` copy. Computed from the user's stored numbers with fixed rules. Tapping the card loads that shape into the board as a starting point; nothing else changes. The card is hidden until the user has both income and at least one cost.
- **AC-8**: The next match can be played from a saved tactic. The write sets `source_kind = 'tactic'` with `tactic_id` and `tactic_version_id`, copies `shape_name`, and writes one line per spot whose planned amounts follow the two step rule and sum to income exactly.
- **AC-9**: When a tactic's defense share cannot cover the user's real costs, the board warns and shows the shortfall, and playing refuses with `unable_to_cover`. No partial match is ever written. Because the DEF zone total is locked to the cost pool, no share change can fix this: the warning copy points the user to a base formation with a bigger defense share, or to their costs and income.
- **AC-10**: The user can rename a tactic, and can delete one after a confirmation. Deletion is a soft delete: matches already played keep their tactic reference and their version rows, and the deleted tactic disappears from the board, the picker, and the cap count.
- **AC-11**: A signed in user cannot read or write another user's tactic by any path: not by guessing a `tactic_id`, not by passing a `user_id`, not through the play function.
- **AC-12**: The board is usable on a phone and with a keyboard. Amounts render through `MoneyText`, no hex literals appear outside the permitted raw layer, and any motion is gated by `prefers-reduced-motion`.

## Options considered

### Option 1: Reuse spec 0004's tactic tables, extend play_match, put the rules in the domain

Build no new tables except one column and one view. The board reads library rows or a saved split, edits share values in the client draft, and computes amounts in `src/domain`. Saving writes the existing tables through Server Actions under the grants that already exist. Playing reuses spec 0007's single atomic function, dropped and recreated with an optional tactic version argument and a spot count read from the data instead of the hardcoded twelve.

**Pros**:

- The snapshot design from spec 0004 pays off exactly as intended, so history stays honest with no new machinery.
- One play path means one set of money invariants, so the tactic route cannot drift from the library route.
- Editing state lives in the client draft, the same pattern spec 0007 already proved, so nothing new to store for an unfinished edit.

**Cons**:

- Touches shipped `play_match`, which carries regression risk against the first match loop.
- Two representations of a split (library rows and a JSONB array) means the validation branch has to check against the right one.
- A JSONB split cannot be joined positionally in SQL, so any future per position tactic report needs a new table.

### Option 2: One normalized tactic_position table, no JSONB

Replace the JSONB split with a real child table holding one row per spot, so the board and the pitch renderer read the same shape of data for library and tactic sources, and reports can join.

**Pros**:

- One data shape everywhere, positional joins and per spot SQL work immediately.
- Row level constraints per spot instead of one trigger over a whole JSONB value.

**Cons**:

- Discards a shipped, migrated, tested table design for no user visible gain, and needs a backfill migration for a table that has no real rows yet.
- A save becomes eleven inserts to keep atomic, which pushes toward a second RPC anyway.

### Option 3: Application level writes under row level security, no function change

The tactic tables already grant insert, update, and delete to `authenticated` with owner policies, so the board's writes go straight through the user's own session exactly as spec 0007's cost and stream actions do, with no new function. For playing, add a second RPC for tactic sourced matches and leave `play_match` alone.

**Pros**:

- The shipped first match loop stays untouched.
- Zero new database surface for the save path, since the grants and policies already exist.
- Less time spent reasoning about one function carrying two sources.

**Cons**:

- Two copies of the income, currency, sum, and defense checks, which is precisely how money code acquires a silent disagreement between preview and stored row.
- A separate action chain is not a transaction, so a tactic match could commit without its lines.

## Decision

**Chosen option**: Option 1: Reuse spec 0004's tactic tables, extend play_match, put the rules in the domain

Build the board on the tables that already exist, add one `deleted_at` column plus one emergency fund view, recreate `play_match` with a tactic branch that reads its own spot count, and put every new rule (share changes, warnings, suggestion) in a pure `src/domain/tactics.ts`.

**Implementation skills**: `supabase` (global, `~/.claude/skills/supabase/`) · `vitest` (`antfu/skills`, `.claude/skills/vitest/`) · `ask-sonner` (global, `~/.claude/skills/ask-sonner/`) · `impeccable` (global, `~/.agents/skills/impeccable/`)

## Rationale

The one requirement this feature cannot compromise is that a month's plan is all or nothing and that a past month never rewrites itself. Spec 0004 answered that with pinned version rows plus one atomic function, so any option that adds a second write path weakens the guarantee it was built to give. Option 3 is the cheapest to start and the most expensive to live with: two copies of the money checks will disagree, and the disagreement shows up as a user's pitch not matching their stored plan.

Option 2 is the better data model on paper and the worse decision today. The JSONB split already exists with a summing trigger and its own security policies, nothing depends on positional joins yet, and replacing a shipped migration to satisfy a report nobody has asked for is speculative work. Spec 0004 already recorded this as a known limit with a route back through `/architect`, and that route stays open.

Coaching rather than gatekeeping follows the product line in the scope (plans and tracks only, never moves money). Blocking a save on a risky shape would also forbid the deliberately defensive plan the product celebrates, so warnings fire inline and at review, and the only hard refusals stay the arithmetic ones: a share total that will not add up, costs a shape cannot cover, and a currency mismatch.

Rules based suggestions beat a model here on every axis that matters for a money tool: deterministic, testable, no cost per read, and no user figures leaving the app. Fixed thresholds are acceptable because 3 months, 6 months, and the 50 percent line are product copy the scope already commits to. Making them tunable in the database would be premature, but `src/domain/tactics.ts` keeps them as named constants so debt mode (feature 8) can revise them in one place.

Per position editing on the pitch, with steppers rather than drag, is the honest middle. Dragging a share on the field is the most football like and the most work (hit targets, pointer capture, and a full keyboard equivalent for the same action). Plain number inputs read as a spreadsheet. Steppers plus an exact field reuse the walk's `AmountField` idiom and are accessible on day one.

**State transitions**:

- Tactic head: `live → deleted` when the action sets `deleted_at`. No restore path in this slice.
- Tactic version: insert only. A new version sets `is_current` true and the existing trigger demotes the previous one. A split is never updated in place (spec 0004's rule, restated here as a build constraint).
- Match: unchanged from spec 0004, `(none) → active → superseded`, driven by `play_match`.

**Interface surface**. One page read plus four Server Actions. The read is not an action: Next.js Server Actions must be async functions used by client components, so `readBoardContext` is a plain server side helper called by the page and the layout, using `requireClaims()` for identity and the read only client. The four actions are built with `authedAction()`, none accepts a user id, and the identity comes from `getClaims()`.

Validation with Zod 4 schemas added to `src/lib/schemas.ts`. Expected failures return an `ActionResult`, they never throw. `invalid_split` covers: a basis point total off 10000, a role outside the five, a gap or duplicate in `spot_index`, a share outside 0 to 10000, a count that does not match the base shape's spot count, or a DEF zone basis point total that differs from the base shape's DEF total.

`playSavedTactic` reads the tactic's current version itself, computes the lines with the same domain call the preview uses, and calls `play_match(null, lines, versionId)`. `tactic_stale` is the specific case where the version passed is no longer the head's current one (a second save landed between the page read and the play). A tactic id that is missing, soft deleted, or owned by someone else is `not_found`, never a leak of its existence.

**Board behaviour (the rules the client draft must hold)**. All of it lives in `src/domain/tactics.ts`, so the client preview and the server check read from one implementation. The server validates against these rules rather than re running them: re applying a delta on a draft that already satisfies them could move shares the user chose.

- Raising non DEF spot _n_ by _d_: `spot[n] += d`, then `-d` from BENCH. If BENCH would go below 0 it goes to 0 and the rest comes from the largest other non DEF spot, then the next largest. Ties break on the lowest `spot_index`, the same rule `src/domain/money.ts` uses for its largest remainder handout. If everything except the DEF zone and spot _n_ is 0, the edit is clamped at the ceiling.
- Lowering non DEF spot _n_ by _d_: the whole delta goes to BENCH, which has no ceiling problem, so the give back path is always BENCH.
- The ceiling for any non DEF spot is `10000 - DEF zone total`, because the DEF pool is locked. The board shows that figure when a clamp bites, with the words "your costs hold the rest".
- Editing BENCH: raising BENCH pulls from the largest non DEF, non BENCH spot. Lowering BENCH pushes the delta to that same spot. BENCH is never its own counterparty.
- Editing a DEF spot: the delta moves to or from the largest other DEF spot, so the zone total, and therefore the cost pool, never changes.
- Typing an exact share follows the same rules as the equivalent delta, clamped to 0 and to the ceiling.
- The board's total readout is always 10000 by construction, so a save is never blocked by arithmetic.

**Key invariants** (database enforced unless noted):

- A tactic version's split sums to 10000 basis points (the shipped statement level trigger), and exactly one version per tactic is current (the shipped partial unique index).
- A saved tactic's spot count, `spot_index` sequence, and DEF zone basis point total match its base shape (new: validated in `saveTactic`, since JSONB cannot express it). This is also what guarantees no zone's basis points can total 0, which is what keeps `allocate`'s division safe.
- A match's lines sum to income exactly, and the DEF planned total equals the current fixed cost total (spec 0004, unchanged).
- One active match per user per period (spec 0004, unchanged).
- A user holds at most 5 tactics with `deleted_at is null` (enforced in `saveTactic`; the count is re read in the same action, so a race can overshoot by one under two simultaneous saves, which is accepted as cosmetic, not monetary).
- A deleted tactic is invisible to every read path but its version rows remain, so a played match can still render its pinned plan (application rule, plus the soft delete column). Its name stays reserved by the shipped unique constraint.
- A match played from a tactic references only the version it was played with; no later edit can change what that match shows (spec 0004's snapshot rule).
- The client never supplies a user id, a period, a currency, a version id, or a planned amount that the server does not re derive (project rule).

**Security model**: signed in only, one writer per own data. `user_tactic` and `user_tactic_version` keep their existing owner policies, and they are already granted `select, insert, update, delete` to `authenticated` (the migration revokes the defaults at line 561 then grants explicitly at line 587), so Server Actions write them through the user's own session under RLS exactly as spec 0007's cost and stream actions do, with an explicit `user_id` filter on every statement as well. No service role client is introduced. `play_match` stays `security definer` in `public` with an empty search path, execute granted to `authenticated` only, and every statement filtered by `(select auth.uid())`. The new tactic branch resolves the version through its head and confirms `user_id` and `deleted_at is null` before reading the split, so a guessed `tactic_version_id` from another user returns `not_found` rather than a plan. The `gk_fund_progress` view exposes only rows the caller can already see and gets the same revoke plus explicit grant treatment as the shipped progress views. No new secrets, no new environment variables. No regulated data class applies (the app never connects to a bank or moves money), but the project rule stands: no financial amount reaches a log or an analytics event. Isolation tests for the new column, the new view, and the new function branch ship in the same PR as the migration, per the project's RLS rule.

**Configuration required**: no new environment variables, no new secrets, no new dependency. One migration that adds a column, a view, and a replaced function, then `pnpm db:types` to regenerate `src/lib/supabase/database.types.ts`. No third party account must be created before coding begins.

**Critical test scenarios** (each maps to an acceptance criterion):

- Happy path: open `4-4-2` on the board, raise Striker by 250 basis points, watch BENCH fall and the naira figure rise on the pitch, save as "My 4-4-2", play it. The match carries `source_kind = 'tactic'`, twelve lines, and planned amounts summing to income. Verifies **AC-1**, **AC-3**, **AC-4**, **AC-8**.
- Normalisation edge: drive BENCH to 0 and keep pushing a share up; the take over moves to the largest other non DEF spot, the total still reads 10000, and no spot goes negative. Verifies **AC-4**.
- Defense pool: raise one defender's share, confirm the DEF zone total and every DEF amount are unchanged while the split between the two defenders moves. Verifies **AC-1**, premise note behaviour.
- Warning path: costs at 60 percent of income, GK share dragged to 0. Both inline warnings appear, the save still succeeds, and the same warnings reappear on the review step. Verifies **AC-5**.
- Refusal path: costs above what the shape's defense share can cover. The board shows the shortfall, `playSavedTactic` returns `unable_to_cover` with the shortfall, and no `match` or `match_line` row exists afterwards. Verifies **AC-9**.
- History path: play a tactic in month one, edit it to a different split, re read month one. The earlier match renders its own pinned amounts. Verifies **AC-2**, **AC-3**.
- Fund nudge: log GK actuals on active matches until the fund reaches 3 months of the last active match's frozen DEF total. The one card appears in its comfortable state with a working tap that loads `4-3-3` into the board, and nothing is written until the user saves. Verifies **AC-6**.
- Fund edge: a user with no logged actuals, and a user whose fixed costs are 0, each get no nudge and no divide by zero. Verifies **AC-6**.
- Suggestion: a user with an outstanding debt sees `5-4-1` recommended with the debt reason, even when their fund is also comfortable (debt outranks the fund in the fixed order). A user with no debt and a full fund sees `4-3-3`. A user with high costs and a thin fund sees `5-3-2`. A steady user sees no card at all, and neither does a user with no income or no costs. Verifies **AC-7**.
- Normalisation lower path: lower a striker's share; BENCH rises by the same amount and the DEF zone is untouched. Verifies **AC-4**.
- BENCH edit: raise BENCH; the largest non DEF, non BENCH spot gives the difference, and BENCH is never its own counterparty. Verifies **AC-4**.
- Ceiling: push one non DEF spot up until everything else except DEF is 0. The edit clamps at `10000 - DEF zone total`, the board names the figure, and the total still reads 10000. Verifies **AC-4**.
- Server validation: a payload whose DEF zone total differs from the base shape, or whose length differs from the base shape's spot count, is refused as `invalid_split` and writes no version row. Verifies **AC-2**, **AC-4**.
- Name reserved: delete a tactic named "My 4-4-2", then try to save a new one with that name. It is refused as `name_taken` and the copy explains that a deleted name cannot be reused. Verifies **AC-10**, **AC-2**.
- Play payload tamper: a call to `play_match` with a valid `p_tactic_version_id` and lines whose basis points differ from the pinned split is refused with `validation`, and no match row exists. Verifies **AC-11**.
- Stale play: read the board, save the tactic again from a second tab, then play from the first tab's stale view. The action answers `tactic_stale` and the user replays from the refreshed board. Verifies **AC-3**.
- Limits: a sixth save refuses with the cap message, a duplicate name refuses with `name_taken`, a 40 character name fails Zod before any write, and a name supplied on an edit is ignored. Verifies **AC-2**.
- Auth and permission: a second user's `tacticId`, `tactic_version_id`, and payload carrying a `user_id` field are each refused, the first two with `not_found` and the last with a validation error, and the isolation suite proves neither read nor write crosses users. Verifies **AC-11**.
- Delete: deleting a tactic an active match references keeps the match and its lines intact, removes the tactic from the board and the picker, and frees a slot under the cap. Verifies **AC-10**.
- Reachability: the app home navigation shows the board entry, and a phone viewport tap reaches `/app/tactics` in one step. Verifies **AC-12**.
- Regression guard: every spec 0007 `play_match` test still passes against the replaced function, including the library branch, the twelve spot wording, and the correction path. Verifies **AC-8**.
- UI and accessibility: the board on a phone viewport, stepped entirely by keyboard, amounts formatted through `MoneyText`, and identical layout under `prefers-reduced-motion`. Verifies **AC-12**.

## Consequences

**Positive**:

- The user owns the plan instead of borrowing one, which is what makes a monthly return plausible.
- Amounts shown while editing turn a percentage choice into a money choice.
- Snapshot history is preserved for free, because spec 0004's pinned versions are used rather than reinvented.
- One play path means one set of money invariants, so the preview and the stored plan cannot quietly disagree.
- The same fund and suggestion rules are ready for Season view and debt mode, in one domain module.

**Negative / tradeoffs**:

- Shipped `play_match` is replaced, not merely added to: a new argument changes the signature, so the migration drops and recreates it. The first match loop carries real regression risk, and a forgotten grant or `search_path` line breaks the shipped play path outright. Mitigation: the recreation is one file that copies the shipped header's grants exactly, and step 9 runs the whole spec 0007 suite against it as a gate.
- The fund nudge reads actuals, so it stays hidden until a user logs a GK payment. That is spec 0004's honest definition, and it costs this feature some of the liveliness a planned based rule would have had.
- A deleted tactic's name stays reserved by the shipped unique constraint, so a user who deletes then tries to reuse the name sees `name_taken`. Accepted rather than dropping a shipped constraint; the copy explains it.
- The board needs a navigation entry of its own. Nothing in the app links to `/app/tactics` today, so without it the page ships unreachable.
- A tactic renders its base shape's pitch layout, because the coordinate table is keyed by formation name. A tactic cannot invent a new shape, which the fixed position count already required anyway.
- Two representations of a split (library rows and JSONB) means validation and rendering must pick the right source in three places.
- Soft delete adds a `deleted_at is null` predicate to every tactic query and to the cap count. A forgotten predicate shows a deleted tactic, which is cosmetic but visible.
- The 5 tactic cap is enforced in the action, not the database, so two simultaneous saves could reach 6.
- JSONB splits still cannot be joined positionally, so a per position tactic report in Season view needs a new table and a route back through `/architect`.
- Editing a DEF share does not change the defense pool, which needs explanation in the UI copy and will still confuse some users.
- Suggestion thresholds are fixed code. A product decision to move the 3 month line now costs a spec edit and a deploy.

**Neutral**:

- One migration that adds a column and a view and replaces one function, then `pnpm db:types`.
- New pages under `/app` inherit the service worker rule that signed in pages are never cached, so the board is offline blocked by design.
- No new dependency and no new environment variable.
- `user_tactic.shape_name` remains a text copy, so renaming or deprecating a library shape cannot orphan a tactic.
